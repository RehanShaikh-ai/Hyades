### 2.4 Execution Service (`backend/app/services/action_execution_service.py`)
Per CONTRACT v0.5.1 §3.2, §5.1, §6.1, §6.2, §6.4, §6.5, §6.8, §11.1, §11.2:
- **Two-Phase Lifecycle**:
  - `mode="propose"`: Validates input, runs handler proposal logic, generates cryptographically secure 32-byte URL-safe token, stores SHA-256 hash in `action_proposals`, sets 15-minute expiration, and returns `ActionResultEnvelope(status="proposed", proposals=[...])`.
  - `mode="commit"`: Verifies SHA-256 hash match, enforces expiration check, rejects already-committed or already-rejected proposals (409 Conflict), executes commit atomically, creates `ActionChangeSet`, and marks proposal committed.
  - Raw confirmation tokens are returned in the propose HTTP response only and **never stored in the database**.
- **Undo Engine**:
  - Verifies change set exists in workspace, rejects already-undone change sets (409 Conflict), executes reverse operation, marks change set `undo_status="undone"`, and returns `UndoResponse`.
- **Cancellation**:
  - `POST /actions/executions/{id}/cancel` transitions active executions to `status="cancelled"`.
- **Workspace Concurrency Limiting (§11.2)**:
  - Configured `ACTION_MAX_CONCURRENT_PER_WORKSPACE = 2` in `Settings`. If >= 2 executions are active/running in a workspace, new execution requests are rejected with `429 Too Many Requests`.
- **Idempotency Deduplication (§11.3)**:
  - Enforces `idempotency_key`. Re-submitting identical requests returns the existing execution without re-executing.

### 2.5 API Endpoints (`backend/app/api/v1/actions.py`, mounted in `backend/app/api/v1/router.py`)
- `GET /api/v1/actions` — Canonical catalogue (37 actions)
- `POST /api/v1/actions/{action_id}/execute` — Unified execute endpoint (read, propose, commit)
- `GET /api/v1/actions/executions/{execution_id}` — Execution status and result envelope
- `POST /api/v1/actions/executions/{execution_id}/cancel` — Execution cancellation
- `GET /api/v1/actions/executions` — Paginated workspace executions
- `POST /api/v1/actions/proposals/{proposal_id}/reject` — Proposal rejection
- `POST /api/v1/actions/change-sets/{change_set_id}/undo` — Revert committed change set
- Hierarchical aliases provided under `/api/v1/workspaces/{workspace_id}/actions/...`.

## 4. Handoff Interfaces for Teammates

### 4.1 For Hamza (Frontend Owner)
- **Catalogue:** `GET /api/v1/actions` returns all 37 action definitions with input schemas, categories, and mutation classifications.
- **Action Execution:** Use `POST /api/v1/actions/{action_id}/execute`.
  - For reads: `mode="read"`, `input={...}`, `idempotency_key="..."`.
  - For writes:
    - Step 1: `mode="propose"`. UI receives `status="proposed"`, list of `proposals` with `changes` and `confirmation_token`.
    - Step 2 (on user confirmation): `mode="commit"`, pass `confirmation_token`. UI receives `status="succeeded"` and `committed_changes[0].change_set_id`.
    - Step 2 (on user rejection): `POST /api/v1/actions/proposals/{proposal_id}/reject`.
- **Undo Button:** Call `POST /api/v1/actions/change-sets/{change_set_id}/undo` to cleanly restore before-state.
