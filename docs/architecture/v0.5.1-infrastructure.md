# Hyades v0.5.1 Infrastructure Architecture

## 1. Executive Summary
This document specifies the infrastructure architecture designed and implemented under **Workstream C (Infrastructure — Ali)** for the Hyades v0.5.1 release.

Workstream C provides the foundational database models, migration pipelines, schema-drift gates, background job processing, workspace concurrency limits, progress persistence, and reproducible benchmark and evaluation fixtures required for safe, high-performance agentic action execution.

---

## 2. Database Schema & Migration Architecture

### 2.1 Relational Architecture
Hyades v0.5.1 introduces persistent action tracking and two-phase proposal execution to support agentic workflows (e.g. `notes.create`, `notes.update`, `notes.archive`, `notes.delete`, `sources.index`).

The schema additions comprise three new tables and one non-destructive table extension:

1. **`action_executions`**:
   - Primary key: `id UUID`
   - Scoped by: `workspace_id UUID` (FK -> `workspaces.id` ON DELETE CASCADE)
   - Lifecycle: `status VARCHAR(30)` (`pending`, `running`, `awaiting_confirmation`, `succeeded`, `failed`, `cancelled`)
   - Progress tracking: `current_stage VARCHAR(100)` and lifecycle timestamps `created_at`, `started_at`, `updated_at`, and `completed_at`
   - Idempotency & Concurrency: unique constraint on `(workspace_id, action_id, idempotency_key)` and index on `(workspace_id, status)`
   - Execution payload & error details: `input_payload JSONB`, optional `result_payload JSONB`, `error_code`, and `error_message`

2. **`action_proposals`**:
   - Primary key: `id UUID`
   - Links to: `execution_id UUID` (FK -> `action_executions.id` ON DELETE CASCADE)
   - Scoped by: `workspace_id UUID` (FK -> `workspaces.id` ON DELETE CASCADE)
   - Security: `confirmation_token_hash VARCHAR(128)` (hash of confirmation token)
   - Status & Expiry: `status VARCHAR(30)` (`pending`, `committed`, `rejected`, `expired`), `expires_at TIMESTAMP WITH TIME ZONE`
   - Diff & preview payload: `proposal_payload JSONB`

3. **`action_change_sets`**:
   - Primary key: `id UUID`
   - Audit association: `execution_id UUID` (FK -> `action_executions.id` ON DELETE CASCADE)
   - Scoped by: `workspace_id UUID` (FK -> `workspaces.id` ON DELETE CASCADE)
   - Change states: `before_state JSONB`, `after_state JSONB`, `affected_item_ids JSONB`
   - Reversible undo state: `undo_status VARCHAR(30)` (`not_undone`, `undone`, `failed`)

4. **`index_jobs` Non-Destructive Extension & Reuse**:
   - Added column: `updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP`
   - **Schema Reuse Confirmation:** The existing `progress` JSONB column is retained and reused for `total_items`, `completed_items`, `failed_items`, and `current_stage`. No duplicate progress columns are introduced.
   - Convenience properties on the SQLAlchemy model read both the v0.5.1 keys and legacy progress keys.

### 2.2 Migration Pipeline & Reversibility
- **Revision Identifier:** `0009_create_v0_5_1_actions_tables.py`
- **Linear Chain:** `0001` -> `0002` -> `0003` -> `0004` -> `0005` -> `0006` -> `0007` -> `0008` -> `0009`
- **Dialect Compatibility:** Compatible with both PostgreSQL 16 (production) and SQLite (testing/local). Uses `batch_alter_table` for column modifications and dialect-aware timestamp defaults.
- **Full Reversibility:** Both `upgrade()` and `downgrade()` routines have been verified under automated test conditions (`backend/tests/test_v0_5_1_schema_drift.py`), confirming 100% preservation of pre-existing records.

### 2.3 Verification Scope
- Migration upgrade/downgrade and preservation were exercised on an in-memory SQLite database populated with representative pre-existing user, workspace, and job rows.
- Alembic's chain and head were checked through revision `0009`; metadata/schema drift checks passed.
- The migration was not applied to a live or shared database. PostgreSQL execution against a disposable copy remains unverified.

### 2.3 Schema Drift Verification Gate
An automated zero-drift verification tool (`scripts/verify_schema_drift.py`) has been added:
- Compares Alembic migration definitions, live SQLAlchemy `Base.metadata` definitions, and database reflection.
- Verifies column types, nullability, unique constraints, and indexes.
- Runs in CI/CD pipeline prior to deployments.

## 3. Asynchronous Job Queue & Progress Persistence

### 3.1 ARQ Worker Infrastructure
Located in `backend/app/jobs/worker.py`:
- Registered job function: `execute_action_job`
- Accepts ARQ context, `execution_id`, and `workspace_id`.
- Coordinates asynchronous background processing for long-running actions.

### 3.2 Progress Persistence Service
Located in `backend/app/services/job_progress_service.py`:
- **`update_index_job_progress(db, job_id, completed_items, failed_items, total_items, current_stage)`**: Atomically updates counts, stage, and `updated_at` on `index_jobs`.
- **`record_retry_progress(db, job_id, retry_count, error_message)`**: Increments retry counts and logs failure details without losing previous progress metrics.
- **`update_action_execution_stage(db, execution_id, current_stage, progress_pct, output_payload)`**: Updates real-time execution progress and stages on `action_executions`.

## 4. Per-Workspace Concurrency Control

### 4.1 Configuration
- Configuration parameter: `ACTION_MAX_CONCURRENT_PER_WORKSPACE` (default: `2`).
- Defined in `backend/app/core/config.py`.
- Exposed in `.env.example` and `docker-compose.yml` across both `backend` and `worker` containers.

### 4.2 Concurrency Enforcement Service
Located in `backend/app/services/concurrency_service.py`:
- **`get_active_workspace_executions_count(db, workspace_id)`**: Queries active executions (`status IN ('pending', 'running')`).
- **`check_action_concurrency(db, workspace_id)`**:
  - Compares active execution count against `settings.ACTION_MAX_CONCURRENT_PER_WORKSPACE`.
  - Raises `AppException(status_code=429, code="CONCURRENCY_LIMIT_EXCEEDED")` if the limit is exceeded.
- **`can_start_execution(db, workspace_id)`**: Non-raising boolean predicate for fast gateway checks.

## 5. Latency Benchmarks & Evaluation Fixtures

### 5.1 Reproducible Benchmark Fixture
Located in `backend/tests/fixtures/v0_5_1_benchmark_data.py`:
- Deterministically generates 1 isolated workspace, 1 test user, 100 notes across 10 academic domains, 20 canonical sources, and 60 content chunks using fixed seed `42`.

### 5.2 Latency Benchmark Suite
Located in `scripts/benchmark_v0_5_1_latency.py`:
- Measures p50, p95, min, max, and mean latencies across 25 iterations for all 10 canonical operations.
- Generates JSON and Markdown outputs.
- Enforces the strict `< 10%` regression threshold required by CONTRACT v0.5.1 §6.2.
- Verified results documented in `docs/benchmarks/v0.5.1-latency.md`.

### 5.3 Golden Questions Evaluation Fixture & Tests
- Fixture: `backend/tests/fixtures/v0_5_1_golden_questions.json` (5 version-controlled domain queries).
- Evaluation test suite: `backend/tests/test_v0_5_1_action_evaluation.py`
  - Validates Recall@5 (observed 1.00 >= 0.80 target).
  - Validates Mean Reciprocal Rank (MRR, observed 1.00 >= 0.70 target).
  - Validates citation precision and database-grounded content hashes.
