## 2. Table Specifications

### 2.1 Table: `action_executions`
Tracks execution state, idempotency, input/result payloads, and lifecycle per §4.1 and §6.1.

| Column | Type | Nullable | Default / Constraints | Notes |
|---|---|---|---|---|
| `id` | `UUID` | No | Primary Key, `uuid.uuid4` | Canonical execution ID |
| `workspace_id` | `UUID` | No | FK → `workspaces.id` ON DELETE CASCADE | Workspace isolation boundary |
| `action_id` | `VARCHAR(100)` | No | None | Dot-notation ID, e.g. `notes.summarize` |
| `status` | `VARCHAR(30)` | No | `pending` | `pending`, `running`, `proposed`, `awaiting_confirmation`, `succeeded`, `failed`, `cancelling`, `cancelled` |
| `initiated_by` | `VARCHAR(20)` | No | `user` | In v0.5.1, must be `user` |
| `idempotency_key` | `VARCHAR(255)` | No | None | Client-supplied idempotency key |
| `input_payload` | `JSONB` / SQLite `JSON` | No | None | Validated input parameters |
| `result_payload` | `JSONB` / SQLite `JSON` | Yes | None | Action execution result |
| `error_code` | `VARCHAR(100)` | Yes | None | Stable machine-readable error code |
| `error_message` | `TEXT` | Yes | None | Safe user-facing error message |
| `current_stage` | `VARCHAR(100)` | Yes | None | Execution stage (e.g. `retrieving`, `generating`) |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()` | Record creation timestamp |
| `started_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Execution start timestamp |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()`, onupdate | Last status update timestamp |
| `completed_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Terminal completion timestamp |

**Constraints & Indexes:**
- Unique Constraint: `uq_action_executions_workspace_action_idempotency` on `(workspace_id, action_id, idempotency_key)`
- Index: `idx_action_executions_workspace_status` on `(workspace_id, status)`
- Index: `idx_action_executions_workspace_created` on `(workspace_id, created_at)`

### 2.2 Table: `action_proposals`
Stores proposed mutations awaiting user review and two-phase server-side confirmation per §4.1 and §6.2.

| Column | Type | Nullable | Default / Constraints | Notes |
|---|---|---|---|---|
| `id` | `UUID` | No | Primary Key, `uuid.uuid4` | Canonical proposal ID |
| `execution_id` | `UUID` | No | FK → `action_executions.id` ON DELETE CASCADE | Parent execution |
| `workspace_id` | `UUID` | No | FK → `workspaces.id` ON DELETE CASCADE | Workspace isolation |
| `action_id` | `VARCHAR(100)` | No | None | Action ID |
| `proposal_payload` | `JSONB` / SQLite `JSON` | No | None | Proposed modifications & affected IDs |
| `confirmation_token_hash` | `VARCHAR(128)` | No | None | SHA-256 hash of raw token (raw token NEVER stored) |
| `status` | `VARCHAR(30)` | No | `pending` | `pending`, `committed`, `rejected`, `expired` |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()` | Creation timestamp |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()`, onupdate | Update timestamp |
| `expires_at` | `TIMESTAMP WITH TIME ZONE` | No | None | Confirmation token expiration |
| `committed_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Confirmation & commit timestamp |
| `rejected_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | User rejection timestamp |

**Constraints & Indexes:**
- Index: `idx_action_proposals_execution` on `(execution_id)`
- Index: `idx_action_proposals_token_hash` on `(confirmation_token_hash)`
- Index: `idx_action_proposals_workspace_status` on `(workspace_id, status)`

### 2.3 Table: `action_change_sets`
Persists committed mutations for auditing, UI result presentation, and safe undo operations per §6.4 and §6.5.

| Column | Type | Nullable | Default / Constraints | Notes |
|---|---|---|---|---|
| `id` | `UUID` | No | Primary Key, `uuid.uuid4` | Canonical change-set ID |
| `workspace_id` | `UUID` | No | FK → `workspaces.id` ON DELETE CASCADE | Workspace scope |
| `execution_id` | `UUID` | No | FK → `action_executions.id` ON DELETE CASCADE | Originating execution |
| `action_id` | `VARCHAR(100)` | No | None | Action that produced this commit |
| `affected_item_ids` | `JSONB` / SQLite `JSON` | No | None | List of UUIDs of modified records |
| `before_state` | `JSONB` / SQLite `JSON` | Yes | None | Snapshot for undo restoration |
| `after_state` | `JSONB` / SQLite `JSON` | Yes | None | State after mutation applied |
| `committed_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()` | Commit timestamp |
| `undo_status` | `VARCHAR(30)` | No | `not_undone` | `not_undone`, `undone`, `non_undoable` |
| `undone_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Timestamp when undo was applied |

**Constraints & Indexes:**
- Index: `idx_action_change_sets_execution` on `(execution_id)`
- Index: `idx_action_change_sets_workspace` on `(workspace_id)`

### 2.4 Existing `index_jobs` Table Extensions (§4.1, §10.1)
The existing `index_jobs` table has:
- `progress`: `JSONB` (added in revision `0006`) containing `{"total": ..., "completed": ..., "failed": ..., "stage": ...}`.
Per §4.1:
> "If an equivalent column already exists, the schema handoff MUST document its reuse. The migration MUST NOT create a duplicate column."

**Reuse Plan:**
The progress reporting model in §10.1 (`total_items`, `completed_items`, `failed_items`, `current_stage`, `updated_at`) maps directly to:
- `progress` JSONB field keys: `total_items`, `completed_items`, `failed_items`, `current_stage`.
- `updated_at` column: To ensure consistency across `index_jobs`, Ali's migration should add `updated_at: TIMESTAMP WITH TIME ZONE DEFAULT func.now()` to `index_jobs` if not already present.
Existing job records and data will be 100% preserved.
