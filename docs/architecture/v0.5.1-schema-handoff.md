## 1. Overview and Migration Gate (§4.1, §4.2)

Per §4.1 and §4.2 of the Hyades v0.5.1 Contract, persistent execution state, proposal state, committed mutation records, and long-running job progress must be persisted in PostgreSQL.

The schema design provides:
1. `action_executions`: Persistent action execution state, idempotency key enforcement, stage tracking, and execution payloads.
2. `action_proposals`: Staging records for proposed mutations awaiting two-phase confirmation tokens, token expiration, and rejection timestamps.
3. `action_change_sets`: Committed mutation records storing affected item IDs, before/after states for auditing, and undo restoration metadata.
4. `index_jobs` extension: Consistent `updated_at` timestamp and structured `progress` JSONB field reuse (`total_items`, `completed_items`, `failed_items`, `current_stage`), guaranteeing 100% preservation of all existing job records.

## 2. Table Specifications

### 2.1 Table: `action_executions`
Tracks execution state, idempotency, input/result payloads, and lifecycle per §4.1, §6.1, and §6.7.

| Column | Type | Nullable | Default / Constraints | Description |
|---|---|---|---|---|
| `id` | `UUID` | No | Primary Key, `uuid.uuid4` | Canonical execution UUID |
| `workspace_id` | `UUID` | No | FK → `workspaces.id` ON DELETE CASCADE | Workspace isolation boundary |
| `action_id` | `VARCHAR(100)` | No | None | Registered action ID (e.g., `notes.summarize`) |
| `status` | `VARCHAR(30)` | No | `'pending'` | Lifecycle: `pending`, `running`, `proposed`, `awaiting_confirmation`, `succeeded`, `failed`, `cancelling`, `cancelled` |
| `initiated_by` | `VARCHAR(20)` | No | `'user'` | Execution initiator (`'user'` in v0.5.1, future: `'agent'`) |
| `idempotency_key` | `VARCHAR(255)` | No | None | Client-supplied logical execution key |
| `input_payload` | `JSONB` / SQLite `JSON` | No | None | Validated action input parameters |
| `result_payload` | `JSONB` / SQLite `JSON` | Yes | None | Action execution output payload |
| `error_code` | `VARCHAR(100)` | Yes | None | Stable machine-readable error code |
| `error_message` | `TEXT` | Yes | None | Safe user-facing error message |
| `current_stage` | `VARCHAR(100)` | Yes | None | Granular execution stage |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()` | Record creation timestamp |
| `started_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Execution start timestamp |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()`, onupdate | Status update timestamp |
| `completed_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Terminal completion timestamp |

**Constraints & Indexes:**
- Unique Constraint: `uq_action_executions_workspace_action_idempotency` on `(workspace_id, action_id, idempotency_key)`
- Index: `idx_action_executions_workspace_status` on `(workspace_id, status)`
- Index: `idx_action_executions_workspace_created` on `(workspace_id, created_at)`

### 2.2 Table: `action_proposals`
Stores proposed mutations awaiting user review and two-phase server-side confirmation per §4.1 and §6.2.

| Column | Type | Nullable | Default / Constraints | Description |
|---|---|---|---|---|
| `id` | `UUID` | No | Primary Key, `uuid.uuid4` | Canonical proposal UUID |
| `execution_id` | `UUID` | No | FK → `action_executions.id` ON DELETE CASCADE | Originating action execution |
| `workspace_id` | `UUID` | No | FK → `workspaces.id` ON DELETE CASCADE | Workspace isolation boundary |
| `action_id` | `VARCHAR(100)` | No | None | Registered action ID |
| `proposal_payload` | `JSONB` / SQLite `JSON` | No | None | Proposed modifications & affected records |
| `confirmation_token_hash` | `VARCHAR(128)` | No | None | SHA-256 hash of confirmation token (raw token NEVER stored) |
| `status` | `VARCHAR(30)` | No | `'pending'` | Status: `pending`, `committed`, `rejected`, `expired` |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()` | Creation timestamp |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()`, onupdate | Update timestamp |
| `expires_at` | `TIMESTAMP WITH TIME ZONE` | No | None | Token expiration timestamp |
| `committed_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Commit timestamp |
| `rejected_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Rejection timestamp |

**Constraints & Indexes:**
- Index: `idx_action_proposals_execution` on `(execution_id)`
- Index: `idx_action_proposals_token_hash` on `(confirmation_token_hash)`
- Index: `idx_action_proposals_workspace_status` on `(workspace_id, status)`

### 2.3 Table: `action_change_sets`
Persists committed mutations for auditing, UI result presentation, and safe undo operations per §6.4 and §6.5.

| Column | Type | Nullable | Default / Constraints | Description |
|---|---|---|---|---|
| `id` | `UUID` | No | Primary Key, `uuid.uuid4` | Canonical change-set UUID |
| `workspace_id` | `UUID` | No | FK → `workspaces.id` ON DELETE CASCADE | Workspace isolation scope |
| `execution_id` | `UUID` | No | FK → `action_executions.id` ON DELETE CASCADE | Originating action execution |
| `action_id` | `VARCHAR(100)` | No | None | Action that produced this commit |
| `affected_item_ids` | `JSONB` / SQLite `JSON` | No | None | List of UUIDs of modified records |
| `before_state` | `JSONB` / SQLite `JSON` | Yes | None | State snapshot for safe undo restoration |
| `after_state` | `JSONB` / SQLite `JSON` | Yes | None | State snapshot post-mutation |
| `committed_at` | `TIMESTAMP WITH TIME ZONE` | No | `func.now()` | Commit timestamp |
| `undo_status` | `VARCHAR(30)` | No | `'not_undone'` | Status: `not_undone`, `undone`, `non_undoable` |
| `undone_at` | `TIMESTAMP WITH TIME ZONE` | Yes | None | Timestamp when undo mutation was applied |

**Constraints & Indexes:**
- Index: `idx_action_change_sets_execution` on `(execution_id)`
- Index: `idx_action_change_sets_workspace` on `(workspace_id)`

### 2.4 Existing `index_jobs` Table Extension & Data Preservation Plan (§4.1, §10.1)

Per §4.1:
> "The table MUST contain: `total_items`, `completed_items`, `failed_items`, `current_stage`, `updated_at`. The implementation MUST preserve existing job data. If an equivalent column already exists, the schema handoff MUST document its reuse. The migration MUST NOT create a duplicate column."

**Reuse & Extension Plan:**
1. **Timestamp Column:** `updated_at: TIMESTAMP WITH TIME ZONE DEFAULT func.now()` added to `index_jobs`.
2. **Progress Model:** Reuses existing `progress` JSONB field (introduced in revision `0006`) containing:
   - `total_items`: integer count of unique logical items
   - `completed_items`: integer count of successfully processed items
   - `failed_items`: integer count of failed items
   - `current_stage`: string stage descriptor
3. **Data Preservation Guarantee:**
   - No existing columns or tables are dropped or modified.
   - All existing rows in `index_jobs` remain accessible.
   - Backwards compatibility is preserved for legacy progress dictionary keys (`stage`, `processed_notes`, `total_notes`, `failed_notes`).

## 3. Migration and Drift Gates Protocol (§4.2, §4.3)

### 3.1 Migration Gate (§4.2)
- Target migration revision: `0009_create_v0_5_1_actions_tables.py`
- Down revision: `0008`
- Applied through Alembic (`alembic upgrade head`)
- Supports both PostgreSQL 16 (production) and SQLite (in-memory unit tests)
- Migration must be fully reversible (`alembic downgrade 0008`)

### 3.2 Schema Drift Gate (§4.3)
Before acceptance, automated drift tests compare:
1. Migration files (`backend/alembic/versions/0009_create_v0_5_1_actions_tables.py`)
2. Application model definitions (`Base.metadata` in `app.models`)
3. Database catalog inspection
Zero drift is verified across all tables, columns, constraints, and indexes.
